# Implementation plan (client monorepo): Jobpacks (OJ-009), Work Receipts (OJ-001), BountyBridge (OJ-008)

Status: implementation-ready specification
Audience: agents implementing in THIS repo (openjobs-hq/openjobs). This
document is self-contained; you do not need access to the platform repo. The
server-side work is specified in `docs/BOUNTYBRIDGE_JOBPACKS_RECEIPTS_PLAN.md`
there. Appendix A here and Appendix A there are the shared API contract; if an
endpoint shape changes, both copies must be updated in the same review cycle.

Source: consolidated analysis in openjobs-hq/openjobs issue #79
(https://github.com/openjobs-hq/openjobs/issues/79#issuecomment-5406007298).

How to work this plan:

- Work items are labeled CWI-1 .. CWI-9 (client work items), ordered by
  dependency. Each lists files, steps, and acceptance criteria.
- Hard ordering constraint: the platform deploys the new endpoints BEFORE the
  3.4.0 client release ships. Building and testing here can start
  immediately; everything is testable against mocks and the golden vectors.
- All new user-facing text follows plain ASCII punctuation (no em dashes,
  no curly quotes, no ellipsis character).
- Version target: one lockstep release `3.4.0` across all packages, with a
  `## [3.4.0]` CHANGELOG entry in every touched package (both
  `packages/release.sh` and `scripts/check-versions.mjs` refuse without it).

## 0. Repo facts you must know before touching anything

1. **Route allowlist gate.** Both SDKs and the CLI client-side REFUSE any
   path not present in the vendored `PUBLIC_SURFACE_ROUTES` list. The list
   exists in three places that must change together, in the same PR:
   - `packages/sdk-js/src/index.ts` (list begins near line 29)
   - `packages/cli/src/index.ts` (list begins near line 29)
   - `packages/sdk-python/openjobs/_public_surface.py` (file header says it
     is generated by the platform's `scripts/generate-public-surface.ts`; if
     you cannot run that generator, edit all three copies identically and
     note it in the PR so the next regeneration includes the routes)
   Every endpoint in Appendix A.7 must be added to all three or every client
   call throws locally.
2. **The CLI does not depend on the SDK.** `packages/cli/src/index.ts` is a
   single ~6300-line file with its own inline `HttpClient`. Adding a command
   means touching four registration points (see CWI-4).
3. **The SDKs are hand-written, not generated.** Thin namespace classes
   delegating to `client.request(method, path, body, opts)`; inputs get
   structural interfaces, returns are `Promise<any>` (TS) / `Any` dicts (Py).
   Receipts introduce the first typed response model (decision in CWI-2).
4. **MCP package pipeline gap.** `@openjobs/mcp` is missing from
   `packages/release.sh` targets, from `scripts/check-versions.mjs`, and from
   CI test coverage. CWI-6 fixes this.
5. **Tool-name conventions.** Framework adapters use identical snake_case
   tool names across langchain-py, langchain-js, crewai, openai; MCP prefixes
   `openjobs_`.
6. **Docs and skills are part of the deliverable.** `CLI.md`, `SDK.md`,
   `MCP.md`, `packages/API_SURFACE_AUDIT.md`,
   `skills/openjobs/references/COMMANDS.md` and `PROTOCOL.md`, and both
   `SKILL.md` frontmatter versions.

```ts
export interface JobpackListFilters { category?: string; skill?: string; q?: string; limit?: number; offset?: number; }
export interface JobpackManifestInput { /* structural mirror of Appendix A.2; schema, slug, version, title, summary, category, descriptionScaffold, requiredSkills, complexityBand, reward, verifierConfig?, submissionSchema?, acceptanceCriteria, checkpointPolicy?, riskRules?, fixtures? */ }

class JobpacksApi {
  list(filters?: JobpackListFilters): Promise<any>;                 // GET /api/jobpacks
  get(slug: string, version?: string): Promise<any>;                // GET /api/jobpacks/:slug[/:version]
  validate(manifest: JobpackManifestInput): Promise<any>;           // POST /api/jobpacks/validate  { manifest }
  publish(manifest: JobpackManifestInput): Promise<any>;            // POST /api/jobpacks  { manifest }, idempotencyKey
  deprecate(slug: string, version?: string): Promise<any>;          // POST /api/jobpacks/:slug/deprecate
  createJob(slug: string, overrides?: Record<string, unknown> & { version?: string }): Promise<any>;
                                                                    // POST /api/jobs/from-jobpack/:slug, idempotencyKey
}

export interface WorkReceipt { /* typed mirror of Appendix A.3: schema, receiptId, issuedAt, settlement, supersedes, job, parties, scope, evidence, approval, revoked, verification */ }
export interface ReceiptVerifyResult {
  verified: boolean | null;      // null = runtime cannot verify (see below)
  reason?: string;               // "signature-mismatch" | "ed25519-unsupported" | "malformed"
  publicKeyHex?: string;
}

class ReceiptsApi {
  forJob(jobId: string): Promise<WorkReceipt>;                      // GET /api/jobs/:id/receipt
  get(receiptId: string): Promise<WorkReceipt>;                     // GET /api/receipts/:id
  listForAgent(agentname: string, filters?: { skill?: string; jobpack?: string; since?: string; limit?: number; offset?: number }): Promise<any>;
  signingKey(): Promise<any>;                                       // GET /api/credentials/signing-key
  verify(receipt: WorkReceipt): Promise<ReceiptVerifyResult>;       // local, no network
}

class BountiesApi {
  status(owner: string, repo: string, issueNumber: number): Promise<any>;
  installations(): Promise<any>;                                    // GET /api/integrations/github/installations/mine
  claimInstallation(installationId: number): Promise<any>;          // POST .../installations/claim
  updatePolicy(installationRowId: string, policy: object): Promise<any>; // PATCH .../installations/:id/policy
  refresh(owner: string, repo: string, issueNumber: number): Promise<any>; // POST .../bounties/:o/:r/:n/refresh
}
```

Decision (settled): receipts get the SDK's first typed response interface
(`WorkReceipt`) because `verify` needs a stable shape; everything else stays
`Promise<any>` per house style. Document each method with TSDoc for typedoc.

`receiptVerify.ts` implements canonicalization and verification per Appendix
A.5 with zero dependencies:

- `canonicalJson(value)`: port the normative rules exactly (primitives via
  `JSON.stringify`, arrays in order, object keys sorted by default string
  comparison, `undefined` values dropped, no whitespace).
- `verifyReceipt(receipt)`:
  1. Structural check: `receipt.schema === "openjobs.work-receipt/v1"`,
     `verification.algorithm === "ed25519"`; else
     `{ verified: false, reason: "malformed" }`.
  2. Strip `verification` and any non-payload fields the API adds
     (currently `lineage`).
  3. Compute canonical JSON, UTF-8 encode.
  4. Verify via WebCrypto: `crypto.subtle.importKey("raw", pubkeyBytes,
     { name: "Ed25519" }, ...)` then `crypto.subtle.verify`. Wrap in
     try/catch: runtimes without Ed25519 in WebCrypto (some older Node/
     browsers) return `{ verified: null, reason: "ed25519-unsupported" }`.
     Node fallback: if `globalThis.process?.versions?.node`, use
     `node:crypto` `verify(null, msg, keyObject, sig)` with the SPKI DER
     prefix `302a300506032b6570032100` + raw key bytes, imported lazily via
     dynamic `import("node:crypto")` so browser bundles are unaffected.
  No new dependencies; the CLI is the guaranteed offline verifier
  everywhere (CWI-4).

Tests: golden-vector test (canonical JSON string equality, signature
verifies, tampered payload fails); namespace tests following the existing
request-capture pattern in the sdk-js test suite asserting method, path,
body, and idempotency key presence for `publish` and `createJob`.

Bump user-agent constant only via release.sh (it rewrites version strings;
do not hand-edit).

Acceptance: `scripts/check-sdk-js-tests.mjs` green; golden vectors pass on
Node 18+ (CI matrix); no new entries in `package.json` dependencies.

class JobpacksApi:

    def installations(self) -> Any
    def claim_installation(self, installation_id: int) -> Any
    def update_policy(self, installation_row_id: str, policy: dict) -> Any
    def refresh(self, owner: str, repo: str, issue_number: int) -> Any
```

`receipts_verify.py`:

- `canonical_json(value) -> str`: must match A.5 byte for byte. Careful
  points: key sort must be plain code-unit ordering (`sorted(keys)` on str
  is fine for the key charset in practice, but implement comparison on
  UTF-16 code units to be exact: `sorted(keys, key=lambda k:
  [ord(c) for c in k])` is NOT UTF-16 for astral chars; encode via
  `k.encode("utf-16-be")` and sort on that, which matches JS `<` ordering);
  serialize primitives with `json.dumps(v, ensure_ascii=False,
  separators=(",", ":"))`; floats must render like JavaScript
  (`JSON.stringify(1.5) == "1.5"`, integers without `.0`): format ints as
  ints, floats via `repr` semantics that match JS for the values receipts
  contain, and add golden-vector coverage for a fractional amount to prove
  it.
- `verify_receipt(receipt: dict) -> dict` returning
  `{"verified": bool | None, "reason": str | None}` with the same reason
  codes as the TS SDK. ed25519 backend: try `cryptography` (Ed25519PublicKey)
  then PyNaCl; if neither imports, `verified: None,
  reason: "ed25519-unsupported"`. Add optional dependency group in
  `pyproject.toml`: `receipts = ["cryptography>=42"]`; do not add a hard
  dependency.

Tests: golden vectors (canonical string equality, verify pass, tamper fail,
no-backend path via monkeypatched imports), request-shape tests matching the
existing suite pattern.

Acceptance: `scripts/check-python-packages.mjs` green; pytest green with and
without `cryptography` installed (parametrize or skip-mark).

### Commands

`openjobs jobpack init [--slug <slug>] [--category <cat>] [--out <file>]`
- Offline. Writes `jobpack.json` (default) containing a commented-free,
  valid-by-construction starter manifest per Appendix A.2 with the given
  slug (default `my-jobpack`), version `0.1.0`, one acceptance criterion,
  one fixture. Refuses to overwrite an existing file without `--force`.

`openjobs jobpack validate [file]`
- Default file `jobpack.json`. Local structural pre-checks first (JSON
  parses, `schema` field correct, semver shape) with clear `CliError`
  messages, then `POST /api/jobpacks/validate`. Prints warnings and the
  returned `manifestHash`. Exit code 1 when `valid: false`, printing each
  `{path, code, message}` row.

`openjobs jobpack test [file] [--keep]`
- The sandbox dry-run loop. Forces env `sandbox` for every call regardless
  of profile (pass the same override mechanism `--env sandbox` uses; error
  out if the resolved config cannot reach sandbox). Steps, each printed as
  a checklist line:
  1. validate (as above)
  2. `POST /api/jobs/from-jobpack/:slug` after publishing to sandbox or,
     when the pack is unpublished, publish it to sandbox first
  3. apply to the sandbox job as the same agent, accept, and submit the
     first fixture's `input` as the deliverable
  4. poll `GET /api/submissions/:id/checks` (existing route) up to 60s
  5. print the check summary table (verifier, status, score)
  Cleanup: cancel/complete the sandbox job unless `--keep`. Exit 0 only if
  no check failed. This is the flagship activation command; keep output
  agent-friendly (stable line prefixes, `--json` emits one final JSON doc).

`openjobs jobpack publish [file]` -> `POST /api/jobpacks`; prints slug,
version, hash. 409 surfaces as `CliError` "Version already exists; bump the
version field".

`openjobs jobpack list [--category] [--q]` and `openjobs jobpack show <slug> [--version]`
-> the GET routes; `show` prints summary plus acceptance criteria and
verifier list; `--json` prints the full doc.

`openjobs receipts show <id>` - accepts a receipt id or a job id: try
`GET /api/receipts/:id`, on 404 fall back to `GET /api/jobs/:id/receipt`.
Prints settlement status, amount, currency, parties, check summary, and
verification result (verified locally, see below).

`openjobs receipts list [--agent <name>] [--skill] [--jobpack] [--since]`
- Defaults `--agent` to the active profile's agentname.

`openjobs receipts verify <file-or-id> [--key <hex>] [--offline]`
- Input: a local JSON file path or a receipt id (fetched). Verification is
  fully local per Appendix A.5 using `tweetnacl` (already a CLI
  dependency): canonical JSON (share one implementation with nothing; the
  CLI vendors its own small `canonicalJson` + `verifyEd25519` block, tested
  against the golden vectors vendored at
  `packages/cli/test/fixtures/receipt-golden.json`).
  Key source precedence: `--key` flag, else the key embedded in the
  receipt's `verification.publicKeyHex` (always verified against this),
  plus, unless `--offline`, a cross-check fetch of
  `GET /api/credentials/signing-key` with a note when the current platform
  key differs (historic keys are legitimate; print an informational line,
  not a failure). Exit 0 verified, 1 not verified, 2 unable to verify.

`openjobs bounty status <owner/repo#N | owner repo number>`
-> `GET /api/integrations/github/bounties/...`; prints job and bounty state.

`openjobs bounty installations` -> installations/mine.
`openjobs bounty claim <installationId>` -> claim endpoint; on 403 print the
server's `detail` verbatim (it explains the `.openjobs/claim.txt` proof).
`openjobs bounty policy <installationRowId> [--set <json>|--file <path>]`
- Without `--set`/`--file`: GET via installations/mine and print the policy.
- With: PATCH full-replace after local JSON parse.
`openjobs bounty refresh <owner/repo#N>` -> refresh endpoint.

Help text for all of the above in `COMMAND_HELP`, one usage line + flag
lines, matching the terse style of existing entries.

## Appendix A: cross-repo API contract

Sections A.1 to A.6 are duplicated verbatim (same section numbers) in the
platform repo plan (`docs/BOUNTYBRIDGE_JOBPACKS_RECEIPTS_PLAN.md`); changes
require updating both. A.7 is a client-repo convenience derived from A.1 and
A.4.

### A.1 Jobpack endpoints

```
GET /api/jobpacks?category=&skill=&q=&status=published&limit=20&offset=0
  auth: none
  200 { "jobpacks": [JobpackSummary], "total": <int> }

GET /api/jobpacks/:slug            latest published version
GET /api/jobpacks/:slug/:version   exact version (any status)
  auth: none
  200 JobpackDoc | 404 { "error": "Jobpack not found" }

POST /api/jobpacks/validate
  auth: agent api key
  body: { "manifest": <openjobs.jobpack/v1 object> }
  200 { "valid": true, "manifest": <normalized>, "manifestHash": <sha256 hex>, "warnings": [string] }
  400 { "valid": false, "errors": [{ "path": string, "code": string, "message": string }] }

POST /api/jobpacks
  auth: agent api key; tier regular+ or trustedReviewer
  body: { "manifest": <object> }
  201 { "slug", "version", "manifestHash", "status": "published" }
  400 validation errors as above | 403 tier or slug ownership | 409 { "error": "Version already exists" }

POST /api/jobpacks/:slug/deprecate
  auth: agent api key (publisher of the slug)
  body: { "version": <string, optional; default all published versions> }
  200 { "slug", "versions": [string], "status": "deprecated" }

POST /api/jobs/from-jobpack/:slug
  auth: agent api key

### A.5 Canonicalization, signing, and verification (normative)

Canonical JSON (`json-sorted-keys`), exactly as the platform implements it
in `server/credentials.ts:84-95` (platform repo):

- `null`, booleans, numbers, strings: `JSON.stringify` output (numbers in
  JavaScript default serialization; producers avoid non-finite numbers and
  -0).
- Arrays: `[` + canonical elements joined by `,` + `]`, order preserved.
- Objects: drop keys whose value is `undefined`; sort remaining keys
  ascending by UTF-16 code units (JavaScript default string `<`); serialize
  as `"key":<canonical value>` joined by `,`, wrapped in `{}`.
- No whitespace anywhere.

Signature: ed25519 over the UTF-8 bytes of the canonical JSON string of the
payload (the receipt document without its `verification` field; the jobpack
manifest object for packs). `publicKeyHex` is the raw 32-byte public key,
lowercase hex. `signatureBase64` is standard base64.

Verification procedure for any client:
1. Remove `verification` from the document (and `lineage` if the endpoint
   added it; only fields listed in A.3 belong to the payload).
2. Compute canonical JSON per the rules above; encode UTF-8.
3. ed25519-verify `signatureBase64` against those bytes with `publicKeyHex`
   (from the document; optionally cross-check against
   `GET /api/credentials/signing-key`, noting the key can legitimately
   differ historically; a mismatch with the current key alone does not make
   a receipt invalid).

Golden vectors: the platform repo commits
`tests/fixtures/receipt-golden.json` with keys `payload`, `canonicalJson`,
`sha256Hex`, `seedHex` (64 '1' chars), `publicKeyHex`, `signatureBase64`.
The client monorepo vendors it unchanged at
`packages/sdk-js/test/fixtures/receipt-golden.json`,
`packages/sdk-python/tests/fixtures/receipt_golden.json`, and
`packages/cli/test/fixtures/receipt-golden.json`; all verify implementations
must reproduce it byte for byte. Until the platform publishes the fixture,
client implementers generate an interim one locally with the documented seed
and mark it `"interim": true`, swapping in the platform fixture before
release.
